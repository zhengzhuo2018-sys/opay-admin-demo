# OPay Admin Coding Rules

- Use React, TypeScript, Vite and `@arco-design/web-react`.
- Reuse Arco primitives before creating custom controls.
- Use semantic variables from `src/styles/tokens.css`; do not place raw brand hex values or arbitrary spacing in page CSS.
- Keep brand state and business status distinct. During the Arco Pro clean-room phase, use the official Arco Pro theme without OPay brand remapping; success, warning and danger still communicate business outcomes.
- Build reusable list, detail, edit, dashboard and modal patterns before duplicating page structures.
- Use `src/components/patterns/ListPage.tsx` for list screens; pass business filters, actions, table content and pagination through its slots instead of recreating the panel shell.
- Treat the OPay screenshots as business-content references, not as visual targets or runtime image assets.
- Preserve verified business modules, fields, states, data relationships, copy, routes and interaction requirements from the OPay source. Rebuild their presentation with native Arco Pro page patterns instead of reproducing the old visual layout.
- Arco authorizes presentation changes, NOT new product content. Do not add headings, descriptions, filters, metrics, totals, warnings, tabs, routes, success screens or workflows just because a reusable pattern has a slot for them. Leave unused slots absent.
- UI content must come from the referenced Figma node or an explicit user-approved addition. Preserve original titles and wording, including surprising labels; flag suspected errors in the handoff/development record instead of silently correcting them. New business copy, fields or behavior requires approval before implementation.
- Hard user requirement: developer explanations must NEVER be written into business UI, including titles, descriptions, banners, tooltips, cards, dialogs, empty states or transient feedback. Source provenance, source conflicts, implementation notes, preview disclaimers, dataset caveats and integration limitations belong only in development/submission documentation and the handoff. Do not relocate a removed explanation to another UI state or surface. Preserve genuine source business warnings without adding commentary. Necessary operational feedback must describe the business outcome rather than the implementation, and must never claim a real financial action succeeded.
- Missing business data must not be invented. If the user explicitly requests complete pagination, repeated existing fixture rows may exercise pagination; keep the source total and record this as a local pagination fixture in the development record, never assert newly sourced records.
- Before changing a confirmed page, identify the exact requested difference and the source node. Keep other confirmed pages unchanged. Run `pnpm check:source-content` before every build: it locks reviewed page/component structure, copy and Page 3 data. A failure requires inspecting and reporting the intentional change; do not regenerate the manifest, copy current hashes automatically or weaken the check merely to pass. Update only the explicitly requested scope after a documented source review.
- New pages must be added to `tests/contracts/source-content.json` with their verified source nodes and a reviewed content/structure baseline. Source review must compare visible modules, titles, labels, hints, warning text, controls and empty/result states, not merely screenshots or successful builds.
- The only exception is an explicitly identified acceptance-test addition or wholly new test case; those may introduce new content according to the supplied test requirements while preserving the established OPay design system.
- Correct obvious screenshot artifacts such as duplicated navigation, repeated support widgets and cropped columns.
- Keep the new presentation layer inside `src/arco-pro`. It may import business-only configuration, types and mock data, but must not import legacy pages, legacy layout components, OPay theme overrides or the old global stylesheet.
- Do not simulate an available Arco control with plain elements. Use native Arco Layout, Menu, Breadcrumb, Form, Table, Pagination, Tag, Card, Tabs, Radio and related controls before adding any custom presentation.
- Keep mock data separate from visual components.
- Run the TypeScript production build after every material implementation step.
- Run `pnpm check:tokens` after styling changes. Raw colors and raw scale values outside the token source are policy violations.
- Update Playwright screenshots only after reviewing an intentional visual change; never update snapshots merely to make a failing test pass.
